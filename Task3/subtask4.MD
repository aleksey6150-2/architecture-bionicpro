## Subtask 4. Кеш-инвалидация + структура хранения

### Структура хранения в S3

```
reports-bucket/
├── user1/
│   ├── 2026-05-21.json
│   ├── 2026-05-22.json
│   └── 2026-05-23.json
├── user2/
│   └── 2026-05-23.json
├── alex.johnson/
│   └── 2026-05-23.json
...
```

- **Префикс по username** — даёт быстрый listing на админке Minio
  и легко делать пер-пользовательские policies при необходимости.
- **Имя файла = watermark** — самое позднее обработанное Airflow
  состояние OLAP. Это и есть версия снапшота отчёта.
- **Никаких "latest" симлинков** — каждый отчёт самодостаточен,
  пользователь всегда получает URL на конкретный watermark.

### Стратегия инвалидации

Используется **версионирование через ключи**:

1. Когда Airflow DAG `user_report_etl` обрабатывает новый день →
   `etl_watermark.processed_through` сдвигается вперёд
2. При следующем запросе `/reports` reports-api строит ключ S3 уже
   с новой датой → `s3.exists(...)` возвращает false → генерим заново
3. Старый ключ `user1/2026-05-22.json` остаётся в S3 (никто не удаляет),
   но reports-api его больше не возвращает → пользователю недоступен
4. Запись в CDN-кеше Nginx для старого URL живёт пока кто-нибудь
   её запрашивает; через 24h `inactive` выселяется

### Почему именно так

| Альтернатива                  | Минус                                                                                                                   |
|-------------------------------|-------------------------------------------------------------------------------------------------------------------------|
| TTL на CDN (короткий)         | Stale-данные между ETL и истечением TTL. Если ETL раз в сутки, TTL = 24h, в худшем случае получается до 48h устаревания |
| Active purge от Airflow в CDN | Нужен `nginx-cache-purge` или подписанный delete-API. Лишняя интеграция                                                 |
| Vary by header                | Не подходит — URL должен быть просто GET'абельный                                                                       |
| Полное удаление старых ключей | Можно добавить как cleanup-job, но не обязательно — храненилище дешёвое                                                 |

Версионирование URL — самый чистый вариант: каждый снимок данных
получает уникальный URL, кеши друг другу не мешают, никакой
координации между сервисами не нужно.

### Чистка старых отчётов (отдельно)

Если в продакшене захочется освобождать место — добавляется отдельный
periodic job (можно тем же Airflow):

```python
# pseudo
keep = 7   # дней
for obj in minio.list_objects('reports-bucket', recursive=True):
    date = parse_date_from_key(obj.object_name)
    if (today - date).days > keep:
        minio.remove_object('reports-bucket', obj.object_name)
```

Не реализовано в рамках задания — текущий объём (десятки KB на день
на юзера) при 8 пользователях даёт сотни KB в сутки. Полгода влезет
в выделенные 512MB CDN-кеша и в default storage Minio без вопросов.
